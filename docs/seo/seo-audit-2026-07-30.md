# SEO Audit: macon170.com

**Date:** 2026-07-30
**Scope:** Full site audit via `/seo audit https://www.macon170.com` (claude-seo plugin v2.2.4), 10 parallel subagents, findings independently fact-checked against the live site.

**Site type:** Nonprofit/community organization (Cub Scout Pack 170, Macon GA) — not a commercial business. It has local-service-shaped signals (fixed meeting venue, service area) but no GBP, no reviews, no walk-in customers. Every subagent was briefed to treat that distinction correctly rather than penalize the site for lacking commercial local-SEO trappings it shouldn't have.

The story: solid fundamentals (clean SSR HTML, good CWV hygiene, genuinely strong E-E-A-T content for a volunteer org) undermined by three near-total gaps — no structured data, no crawl-discovery infrastructure, and no HTTPS enforcement.

---

## Critical (fix immediately)

**1. Plain HTTP is served with no redirect to HTTPS, and no security headers anywhere.**
Verified directly: `curl -I http://www.macon170.com/` → `200` (not redirected), and `https://www.macon170.com/` has zero `Strict-Transport-Security`, `Content-Security-Policy`, `X-Content-Type-Options`, `X-Frame-Options`, or `Referrer-Policy` headers. Note the apex domain (`http://macon170.com/`) _does_ correctly 308-redirect — so the fix logic already exists somewhere, it's just not applied to the `www` HTTP listener.

- **Dependency:** none — this is a Worker-level fix, independent of everything else.
- **Falsifiability check:** `curl -I http://www.macon170.com/` returns 301/308 to `https://`, and the five headers above appear on the HTTPS response.
- **Leading indicator to watch:** Lighthouse "Best Practices" score (currently dragged down by this).

**2. No structured data anywhere on the site (confirmed independently by 5 of the 10 subagents).**
Zero JSON-LD/microdata/RDFa across every page. This is a clean slate — no deprecated types to remove, just additions. The schema subagent produced ready-to-paste `Organization`, `Event`, and `BreadcrumbList` JSON-LD (see Appendix).

- **Dependency:** Event schema depends on `src/data/pack.ts`'s existing typed event data — no new data model needed, just rendering it as JSON-LD.
- **Falsifiability check:** Google Rich Results Test on `/` and `/calendar` shows valid `Organization` and `Event` entities with no errors.
- **Leading indicator:** Search Console → Enhancements report starts showing Event/Organization coverage instead of "no items detected."

**3. No XML sitemap, and robots.txt has zero crawl directives.**
`/sitemap.xml` is a 404; robots.txt exists but contains _only_ AI content-signal comments (no `User-agent`, `Disallow`, or `Sitemap:` line at all). At 18 pages this doesn't block crawling, but it removes the standard signal Search Console uses for coverage diffing, and it's a five-minute fix with `@astrojs/sitemap` since Astro can generate it from the actual route manifest (avoiding drift a hand-written file would have). Also caught: `/events/` (a client-JS-rendered detail shell) should be excluded from the sitemap and given `noindex` — it isn't one of the 18 intended pages but is currently crawlable.

- **Dependency:** none — pure build-config addition (`bun add @astrojs/sitemap`).
- **Falsifiability check:** `/sitemap.xml` returns 200 with 18 (not 19) `<url>` entries; `/events/` returns `noindex` in its meta tag.
- **Leading indicator:** Search Console coverage report shows 18/18 "Indexed" instead of the current ambiguous state.

## High

**4. The homepage/join/calendar links show literal placeholder text "next date is being added" instead of a real date.** Confirmed live on `/`, `/join`, and `/calendar`. This is the exact moment a ready-to-sign-up parent needs a concrete answer — persona scoring flagged this as the single weakest journey (51/100, "Next-Meeting-Date Parent"). Worth checking whether this is a genuine "no upcoming event scheduled" state or a data/fetch bug in the calendar client.

- **Falsifiability check:** the string no longer appears in the homepage/join/calendar HTML when a future event exists in `pack.ts`'s data.

**5. `/calendar` fetches its events API twice per pageview**, and lacks a `<link rel="preconnect">` to `cms.macon170.com` before the client-side fetch — a real correctness/perf bug, not just an optimization. Combined with no reserved layout space for the injected timeline rows, this is a latent CLS risk on slower connections even though it didn't trigger in this lab run.

- **Falsifiability check:** Network tab on a fresh `/calendar` load shows exactly one `GET /api/calendar/v1/events`, and a preconnect hint is present.

**6. LCP is in the "Needs Improvement" band (~3.1-3.2s) on both the homepage and `/calendar`**, gated by render-blocking CSS shared via `BaseLayout.astro`, not by images or slow TTFB (edge cache HIT, 20-83ms). Inlining critical CSS is the single highest-leverage performance fix available.

- **Falsifiability check:** re-run Lighthouse mobile; LCP display value moves toward ≤2.5s.

**7. Trailing-slash redirects (e.g. `/join` → `/join/`) use HTTP 307 (temporary) instead of 301/308 (permanent).** This is permanent site architecture, not a temporary condition — signaling it as temporary weakens link-equity consolidation. (Apex→www already correctly uses 308, so the fix pattern exists in the codebase.)

- **Falsifiability check:** `curl -I https://www.macon170.com/join` returns 308/301, not 307.

**8. Geo-keywords ("Macon") are missing from 3 of 4 key page titles** (`/about`, `/calendar`, `/contact` — only the homepage title includes it), and the site doesn't rank/surface for local queries like "cub scouts macon ga" in a spot-check — Facebook, Yelp, and legacy domains (`cubscoutpack170.square.site`, `pack170.org`) currently own that space instead. This is a strategic question as much as a technical one: worth deciding whether to consolidate NAP across those legacy properties or actively redirect/deprecate them.

- **Falsifiability check:** title tags include "Macon" on `/about`, `/calendar`, `/contact`; manual SERP check shows macon170.com appearing for branded + "near me" queries.

## Medium

- **No Open Graph/Twitter Card tags anywhere** — confirmed by 3 subagents. Matters concretely here since parents share pack links in Facebook groups/PTA chats; link previews currently fall back to no image/generic text.
- **Static hashed assets (`/_astro/*.css`) use `Cache-Control: max-age=0, must-revalidate`** instead of long-lived immutable caching, despite content-hashed filenames making that safe.
- **Homepage hero image has ~49KB of easy savings** even though it already serves WebP with srcset.
- **BeAScout unit-locator zip param (31201) doesn't match the site's stated address zip (31211)** — worth a manual sanity check (may just be a search-radius parameter, not a real mismatch).
- **4 of 6 den leader name fields are blank** in the `/about` leadership roster (Tiger, Wolf, Bear, Arrow of Light) — likely reflects genuinely vacant volunteer roles, but worth confirming with the pack rather than leaving ambiguous.
- **No BreadcrumbList on the `/dens` → `/dens/[den]` hierarchy.**
- **AI content-signal directives in robots.txt are template comments with no actual values set** — `search`/`ai-input`/`ai-train` are all left in an undefined state rather than an intentional yes/no.
- **No passages sized for AI-citation extraction** (134-167 word sweet spot) — content is fragmented into short blocks, capping AI Overview/Perplexity citability.
- **`/join` targets the unwinnable broad term "join cub scouts"** (dominated by national/council pages) without a geo-modifier that would make it winnable on long-tail.

## Low

- IndexNow not implemented (marginal ROI at this scale).
- htmldate's freshness signal reports an identical, suspicious `2026-01-01` "publication date" across every page — not a real last-updated timestamp, but low-stakes since it's not user-facing.
- No Moz/Bing backlink API key configured — free to add, unlocks DA/PA data (currently Tier 0/Common Crawl only, which shows nothing because the site is too small/low-traffic to appear in CC's snapshot — not evidence of a bad backlink profile).
- Nav "active state" styling is ambiguous between "Join" as a persistent CTA accent vs. an active-page indicator.
- `/join` mobile CTA sits close to the fold edge on shorter devices (iPhone SE-class).

## Info (no action needed)

- No FAQPage schema exists anywhere — correctly nothing to flag per current policy (FAQ rich results have no Google SERP benefit as of May 2026); if genuine parent Q&A content is ever added, mark it `QAPage`, not `FAQPage`.
- GBP/reviews/commercial citations are legitimately N/A for this entity type.

## Recommended sequencing

1. **HTTPS/security headers + sitemap** (both pure Worker/build-config fixes, zero content dependency, ship same day)
2. **Schema JSON-LD** (Organization → Event → BreadcrumbList, in that order since Event depends on nothing new)
3. **Fix the calendar placeholder-date bug and duplicate fetch** (product bug, blocks the highest-value user journey)
4. **Critical CSS inlining for LCP**
5. Everything else (titles, OG tags, caching headers, breadcrumbs) can land opportunistically

## What's already working well (confirmed, not assumed)

- Clean server-rendered HTML with no JS-execution dependency for crawlers; correct viewport meta, no zoom-blocking; explicit `width`/`height` on images (CLS protection); fonts preloaded with `font-display: swap`.
- Genuinely strong E-E-A-T content: named leadership roster, specific/non-generic youth-protection claims (two-deep leadership, no one-on-one contact, background checks), transparent citation of Scouting America source material, and six den pages that are legitimately unique (not templated thin content) once diffed directly.
- Accurate, consistent "Scouting America" branding and grade/rank mapping site-wide.
- No Critical mobile/visual issues — clear above-fold CTAs on homepage, /join, and /calendar.

## Note on refuted findings

Two subagents independently reported a "site-wide UTF-8 mojibake bug" (corrupted en-dashes/apostrophes), and one reported an H1 text-concatenation bug ("Cub ScoutPack 170" with no space). Both were checked against the live site directly and refuted:

- The en-dash in "Kindergarten–5th grade" hex-dumps to `e2 80 93` — correctly single-encoded UTF-8, not double-encoded mojibake.
- The homepage H1 markup is `<h1>Cub Scout<br><span>Pack 170</span></h1>` — a legitimate `<br>` line break that a text-only extractor collapsed into a missing space.

Both were artifacts of the subagents' own extraction tooling, not real site defects, and are excluded from the findings above.
